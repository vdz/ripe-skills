# Ripe × Next.js: root-cause findings

The latest Next.js release is 16.4 (2026-10-07). Sources: https://nextjs.org/blog/next-16-4 · https://nextjs.org/blog/next-16

## Part 1: Root-cause findings (draft)

**1. React Router → file-system routing.** Ripe treats the router as a client-side runtime: routes are declared in code and a `setLocation` bridge feeds the URL into Redux so listeners can react to it. In the App Router the URL is resolved **on the server**. The `app/` folder tree is the route table, and each segment gets nested `layout`/`page`/`loading`/`error` boundaries that are rendered as RSC payloads. Client navigation only fetches the segments that differ (16.x added layout deduplication and incremental/partial prefetching). Owning the URL in a client store would therefore duplicate work the framework already does on the server. *Still valid:* "the URL is state", one declarative route map, and pages kept thin. *Tied to the SPA runtime:* the router-to-store bridge and code-declared routes. (https://nextjs.org/docs/app/getting-started/layouts-and-pages)

**2. Redux store → server state plus a small client store.** Ripe's store exists because an SPA has to hold *server data* on the client for its whole lifetime. With RSC, a Server Component can `await` the DB directly (here, through `lib/db`). Mutations go through Server Actions, followed by `revalidatePath`, `revalidateTag` or the new `updateTag`, and the server becomes the source of truth. A global client store that mirrors DB rows then becomes a second cache that can drift out of sync. One more limit: a Redux store is a module-level singleton, which is unsafe across requests on a server, so it has to be created per request inside a client provider. *Still valid:* business logic stays out of components, there is one place per domain (`lib/db/queries`, `lib/cta` registry), and actions are typed and named. *Tied to the SPA runtime:* reducers and selectors as the home of server data. Redux, or `useReducer`/Zustand, stays appropriate for real client-only state such as the flows/wizard engine. (https://nextjs.org/docs/app/getting-started/updating-data, https://redux.js.org/usage/nextjs)

**3. "Listeners load data, not components" → server pages load.** The rule exists so that render code stays pure and I/O is centralised and testable. In an RSC tree, an `async` Server Component that only renders on the server **is** that centralised loading step. It runs once per request, never re-runs on the client, and has no effect waterfalls. The principle survives in a different form: *leaf/client components never fetch; data enters at route or segment entry points through `lib/db`*. Listener-style reactions to events map to Server Actions plus revalidation, and to `after()` for side effects. *Still valid:* the intent behind the rule. *Tied to the SPA runtime:* the listener middleware mechanism.

**4. styled-components → CSS Modules.** Runtime CSS-in-JS generates styles during render through React context. Server Components have no context and no state, and streaming SSR flushes HTML in chunks, so styles have to be collected and injected per chunk through a registry (`useServerInsertedHTML`). Every styled component is also forced to be a `'use client'` component. The result is a larger client bundle and a cap on how much of the tree can stay on the server. CSS Modules (or zero-runtime options such as vanilla-extract/Panda, or Tailwind) compile at build time. *Still valid:* styles co-located per component and one styling approach for the whole app. *Tied to the SPA runtime:* styles generated at runtime from props. Use `data-*` attributes and CSS variables for variants. (https://nextjs.org/docs/app/guides/css-in-js)

**5. config.ts → Zod `env.ts`.** In a Vite SPA, config is public and inlined at build time. Next has two environments: server-only secrets, and `NEXT_PUBLIC_*` values inlined into the client bundle. Leaking a server secret into client code is a security bug. That calls for a parsed and validated boundary, plus the `server-only` package. *Still valid:* one typed config module. *New:* the split between server and public config. (https://nextjs.org/docs/app/guides/environment-variables)

**6. Component tests → Vitest + Playwright.** Async Server Components cannot be rendered by React Testing Library today, and much of the behaviour (RLS, Server Actions, caching, proxy redirects) only exists end to end. Pure logic and Client Components can still be unit-tested; anything that crosses the server boundary needs e2e tests. *Still valid:* test behaviour, not implementation. (https://nextjs.org/docs/app/guides/testing)

**7. CLAUDE/CONTEXT/PROGRESS.md → AGENTS.md.** This is a tooling convention, not a runtime one. AGENTS.md is the cross-agent standard, and Next 16.x adds its own agent tooling: the Devtools MCP, `next upgrade --agent`, and Cache Components Skills. *Still valid:* short, machine-readable project context. Suggestion: keep PROGRESS as the git/PR history and fold CONTEXT into AGENTS.md.

**8. (New in 16) caching and `middleware` → `proxy`.** The implicit caching of Next 13–15 is replaced by opt-in `'use cache'`, `cacheLife` and `cacheTag`, with Suspense holes for dynamic data (PPR). This is the closest Next equivalent to Ripe's "explicit, predictable" ethos, and Ripe skills should encode it. `proxy.ts` runs on Node only. hasulam's `middleware.ts` should be renamed.
